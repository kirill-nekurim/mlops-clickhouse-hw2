# ДЗ4: аналитика транзакций в dbt

Данные из ДЗ2 проходят три слоя: raw `transactions_db.transactions`, очищенная
`stg_transactions` и шесть аналитических витрин. В исходной домашке таблица называлась
`fraud.transactions`; ниже есть подключение к ней без копирования данных.

В репозитории уже есть полный `data/train.csv.xz`: 786 431 строка из соревнования
TETA. Для dbt не нужно заново запускать Kafka: отдельный учебный ClickHouse поднимается
на порту 18123, загрузчик читает тот же файл. Основной compose ДЗ2 работает отдельно.

## Запуск с нуля

Нужны Docker Compose v2, Python 3.10+ и make. Команды из корня репозитория:

```bash
cd dbt
python3 -m venv .venv
source .venv/bin/activate
make install
make up
make load
make check
```

`make check` выполняет `dbt deps`, `dbt seed`, `dbt run`, `dbt test`, SQLFluff
и генерацию документации. Все команды dbt используют `--profiles-dir .`.
Версии: `dbt-core==1.10.15`, `dbt-clickhouse==1.10.3`, `sqlfluff==3.5.0`.
Python-пакеты перечислены в `requirements.txt`, dbt-пакеты зафиксированы
в `packages.yml` и `package-lock.yml`.

Загрузчик сначала пишет во вспомогательную таблицу порциями по 10 000 строк и
меняет raw только после полного чтения файла. Если загрузка прервалась, её можно
повторить. Если raw уже заполнена, повторный `make load` ничего не дописывает.

Посмотреть созданные таблицы:

```bash
docker compose -f compose.yml exec clickhouse clickhouse-client \
  --user dbt --password dbt_local --query 'SHOW TABLES FROM fraud_analytics'
```

Остановить учебный ClickHouse с сохранением данных:

```bash
make down
```

## Если ClickHouse из ДЗ2 уже работает

У исходного проекта HTTP-порт 8123, пользователь `default` без пароля и база `fraud`.
Подключение настраивается переменными окружения, файл профиля менять не нужно:

```bash
export CLICKHOUSE_HOST=127.0.0.1
export CLICKHOUSE_PORT=8123
export CLICKHOUSE_USER=default
export CLICKHOUSE_PASSWORD=''
export CLICKHOUSE_RAW_SCHEMA=fraud
make check
```

В этом варианте `make up` и `make load` не нужны. Источник только читается,
dbt создаёт свои таблицы в отдельной базе `fraud_analytics`. Её имя можно задать
через `CLICKHOUSE_SCHEMA`. Для возвращения к отдельному учебному стенду удалите
эти переменные из текущей оболочки.

## Модели и метрики

- `stg_transactions`: нормализация строк, типов и времени; удаление отрицательных,
  бесконечных сумм, пропусков времени/суммы и меток вне 0/1. Повторяющиеся
  нормализованные операции объединяются. Слой материализован таблицей, чтобы
  шесть витрин и тесты не считали одни и те же хэши заново.
- `mart_daily_state_metrics`: дата и штат; число операций, сумма, средний чек,
  точный P95 и процент крупных операций.
- `mart_fraud_by_category`: категория; число операций и фродов, fraud_rate,
  общая сумма и сумма фрода.
- `mart_fraud_by_state`: штат; fraud_rate, число клиентов и мерчантов, суммы.
- `mart_customer_risk_profile`: условный клиент; первая/последняя операция,
  число операций, fraud_rate, средний чек, сумма и сегмент риска.
- `mart_hourly_fraud_pattern`: ISO день недели и час; число операций, фродов,
  fraud_rate и суммы.
- `mart_merchant_analytics`: мерчант; оборот, средний чек, число клиентов,
  fraud_rate и признак подозрительности.

Все доли — **проценты от 0 до 100**. Крупная операция — сумма от 1000;
порог задаётся переменной dbt `large_amount`. Макрос `amount_bucket` возвращает
SMALL для сумм меньше 100, MEDIUM для [100, 1000), LARGE для сумм от 1000.

Риск клиента: HIGH при fraud_rate >= 5%, MEDIUM при ненулевом числе фродов
и fraud_rate < 5%, иначе LOW. Мерчант подозрительный, если fraud_rate >= 5%
и есть хотя бы два фрода. Это простые правила описания размеченной истории,
а не модель для прогнозирования будущего фрода. На клиентах с малым числом операций
процент нестабилен, поэтому рядом всегда есть размер истории.

В CSV нет card_id или другого надёжного ID клиента. `customer_id` — хэш имени,
фамилии, пола и координат; это приближение, возможны совпадения и разделение одного
клиента при смене адреса. `transaction_id` — хэш нормализованных полей операции,
используется для удаления повторов. Исходное время не переводится между часовыми
поясами: час и дата соответствуют данным CSV.

## Макросы, пакеты и проверки

`dbt_utils` используется для surrogate keys и уникальности составных ключей.
`dbt_date` — для ISO дня недели. Для него есть небольшой dispatch-макрос
`clickhouse__day_of_week`, поскольку пакет не содержит этой реализации для ClickHouse.
`dbt_expectations` проверяет непустой staging и диапазоны суммы и часа.

Описаны все модели и их колонки. Базовые тесты проверяют обязательные значения,
уникальность ключей и допустимые категории. Составные ключи: дата + штат и
день недели + час. Seed `states` содержит 50 штатов и DC; relationship-тест
проверяет коды штатов, кроме явно отмеченного UNKNOWN.

Singular SQL-тесты в `tests/`:

- нет отрицательных и нечисловых сумм;
- fraud_rate во всех пяти витринах фрода лежит в [0, 100];
- количество операций и сумма каждой витрины совпадают со staging;
- количество фродов каждой соответствующей витрины совпадает со staging;
- сегменты риска соответствуют описанным границам.

Native unit tests dbt:

- очистка, удаление дублей, день недели и границы сегментов суммы 100/1000;
- две операции, один фрод: 50%, корректные общая и фродовая суммы;
- все три сегмента риска, включая HIGH ровно при 5%.
- точный P95, средний чек и процент крупных операций на маленьком примере.

```bash
make test       # data tests и unit tests
make unit-test  # только unit tests
make lint
```

SQLFluff использует ClickHouse dialect и dbt templater. Имена функций ClickHouse
чувствительны к регистру, поэтому правило их переименования отключено. Остальные
правила проверяют форматирование, алиасы и структуру SQL. Исправление: `make format`.

Pre-commit находится в корне репозитория:

```bash
cd ..
pre-commit install
pre-commit run --all-files
```

Для dbt templater должен быть доступен ClickHouse и уже выполнен `make deps`.
